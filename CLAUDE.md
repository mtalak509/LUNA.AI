# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What this is

**LUNA** — a personal work assistant for operating on documents and reports within a
filesystem, with the primary surfaces being a **CLI** and a **web UI**. Architecturally it is
a thin *harness* around an LLM agent, built on **LangChain v1.x** and **LangGraph 1.x**, with a
**filesystem-first** state model.

Origin: LUNA is a fork of `analyzer-agent-service`. It reuses the parent's agent core and V2
architecture but is now an **independent, open-source project** that evolves on its own — do
**not** carry decisions over from the parent by default.

Current codebase reality: the agent works with **the user's files by path** via one set of
ordinary file tools (`read` / `write` / `edit` / `ls` / `find` / `grep` / `rm`) over a filesystem
working zone. There is no privileged document, no special file format, and no domain schema —
the tools are general-purpose.

## Parent release digests

Periodically, digests of the parent project's (`analyzer-agent-service`) releases land in
`digests/<version>/digest.md` (generated by the
`parent-release-digest` skill). They summarize what shipped in a parent release and how it was
built. Treat them as **scouting material, not a backlog**: LUNA is independent and does not
inherit the parent's decisions — a digest is input for deciding whether a given idea is worth
porting, on LUNA's own terms (filesystem-first, no DB, no domain schema). When asked to analyze
or act on a digest, read it from `digests/` and weigh each item against LUNA's architecture
before proposing anything.

## Key facts about the runtime

- **Single entrypoint:** the FastAPI agent server `core.app.server:create_app` (uvicorn,
  `--factory`, port 8000). There is **no database, Alembic, or separate orchestrator process** —
  they were removed; the agent server is the whole backend.
- **MainAgent** is one `create_agent` instance per session; **subagents** run as in-process
  `asyncio.Task`s spawned from the `delegate_to_subagent` tool (cold logical context, own message
  list). Subagents advise via `{summary, artifacts}`; they never write into the main agent's workspace.
- **LLM inference:** provider selected by `LLM_PROVIDER` (`build_chat_model`) — `gpustack`
  (default, vLLM via GPUStack on the **Responses API**), `openrouter` (public OpenAI-compatible
  gateway, Chat Completions), or `ollama` (local, Chat Completions). All three are built with
  `ChatOpenAI`. Config from env / `.env` (`core/config.py` → `InfraConfig`).
- **Middleware stack:** Permission Mode (plan/act — hides+gates write tools), Decision Mode
  (confirm/accept-all — gates any `is_write=True` tool), context injection (working-context
  envelope in the message tail), history compaction (custom step, no checkpointer).
- **RAG:** two-step Qdrant knowledge-base search (preview → full); `fastembed` for local vectors.

## Repository layout

- `core/agent/` — agent core: `base.py` (BaseAgent / `run_stream`), `middleware/`, `tools/`
  (flat pool: files, RAG, HITL, delegation), `compaction.py`, `checkpoint.py`.
- `core/app/` — FastAPI server (`server.py`), session-scoped `routes/`, SSE (`sse.py`).
- `core/services/` — RAG, embedding, Qdrant services. `core/clients/` — HTTP clients.
- `core/procedures/` — agent prompts (`main_agent.*.md`, subagent `agent.md`s).
- `cli/` — self-contained CLI REPL package (`python -m cli` / `luna`): drives one in-process
  session through `AgentSession` directly, no HTTP. Shared build code lives in
  `core/agent/bootstrap.py`.
- `devfront/` — built-in web UI (static assets served by the same FastAPI process): `static/`
  (`index.html`, `style.css`, `app.js` + ES modules in `static/js/`, self-hosted fonts and icons
  in `static/assets/`), `tests/` (Node's built-in runner), `docs/README.md` (API contract + UI
  decisions); `session.py` is a thin back-compat re-export of `core/agent/bootstrap.py`.
- `tests/` — pytest suite (mirrors `core/` structure).
- `tests/evals/` — live end-to-end regression scenarios (DeepEval), one folder per feature; see
  `tests/evals/README.md`.
- `docs/` — English narrative documentation (architecture, runtime, storage, tools, modes/HITL,
  interfaces, frameworks) + the tech-debt registry.
- `planning/` — idea cards: the decision log of what to build (see `planning/README.md`).
- `specs/` — specs and implementation plans, one folder per feature (git-ignored, local).

## Conventions

- **Python 3.11**, line length **100**, ruff + black + mypy (`disallow_untyped_defs = true`).
- **No database layer.** The DB / Alembic / orchestrator were removed — the agent server is the
  whole backend and session state is materialized on the filesystem. Don't reintroduce a database
  or a LangGraph checkpointer.
- **Windows-first dev environment** (PowerShell). Watch for file-handle locks (e.g. an open log
  file blocks `shutil.rmtree`) and CRLF/LF line endings.
- **Code comments in English only** — and only when they genuinely clarify; avoid noise. Legacy
  Russian comments are not translated wholesale — bring a comment to English when you touch it.
- **Docs are English, plain-language narrative.** The `docs/` documentation is written in English
  as connected prose — simple language, no heavy abstractions, aimed at a reader building a mental
  model (not a spec dump). Keep new/updated docs in that voice. The one exception is
  `docs/tech-debt.md`, a working registry kept in Russian. README and code identifiers are English.
- **Clean, concise, OOP-oriented code.** No commented-out or dead code — deprecate (with a shim
  where back-compat matters) or delete; history lives in git.
- **Modularity by cohesion.** Extract cohesive groups of a service's helpers into their own
  module-seams (named for the concept, e.g. `fs_paths` — never a `utils`/`helpers` dumping
  ground). Extract by responsibility, not by helper count; a single-use helper bound to a
  service's state stays a private method. Dependencies point downward — no back-imports, no cycles.
- **Specs and plans live in `specs/<feature>/`.** One folder per feature, named for it
  (e.g. `specs/file-tools/spec.md`, `specs/file-tools/plan.md`). This overrides any skill's default
  location (e.g. superpowers' `docs/superpowers/`).
- **Live regression tests for every feature.** A new feature ships with unit tests *and* end-to-end
  scenarios run against the live stack (real LLM, real agent loop), marked `integration` and
  excluded from the default run. One run per scenario, no MLflow. Framework: **DeepEval**
  (`eval` extra) with an **LLM judge** — a model on OpenRouter set by `EVAL_JUDGE_MODEL`, always
  different from the agent's model. No tracing yet (would need a `callbacks` hook in core), so
  trajectory metrics (`TaskCompletion`, `StepEfficiency`) are out for now. Every check is a
  DeepEval metric, so it shows in the report:
  - *Workspace State* — deterministic: workspace after the run equals `expected/<scenario>/`.
  - *Tool Correctness* — deterministic: expected tools called, in order.
  - *Argument Correctness* — judge: tool arguments fit the request.
  - *Correctness* (`GEval`) — judge: the scenario's `judge_criteria`, step by step.

  **Claude oversees the judge**: after a run, reads the scores/reasons next to the artifacts in
  `tests/evals/.runs/<feature>/<scenario>/` and flags verdicts that don't match them; when adding
  criteria, checks the judge on a deliberately bad case (negative control) — a judge that can't
  fail is useless. The user approves `judge_criteria` for new scenarios.

  Layout: `tests/evals/<feature>/` with `test_<feature>.py`, `.dataset.json` (hand-written
  goldens — regression scenarios with concrete expected effects, not `deepeval generate`
  synthetics), `workspaces/<ws>/` (start state) and `expected/<scenario>/` (end state). Shared
  pieces: `tests/evals/` `conftest.py`, `harness.py` (`ScenarioRunner`), `metrics.py` (judge +
  metrics). Details: `tests/evals/README.md`.

## Commit style — Conventional Commits (English)

Format:

```
type(scope): short imperative summary
```

- `type` ∈ `feat` | `fix` | `refactor` | `chore` | `docs` | `test` | `perf` | `build` | `ci`.
- `scope` — the affected area (e.g. `attachments`, `middleware`, `app`, `tools`, `rag`, `docs`,
  `release`).
- Summary — imperative mood, lowercase, no trailing period, English.
- **No co-authorship or attribution, ever.** Never add `Co-Authored-By:` trailers,
  "Generated with …" lines or any other AI/tool attribution to commit messages or PR
  descriptions. This overrides any default attribution guidance.

Examples:

```
feat(attachments): implement file upload for turn requests
fix(middleware): prevent KV cache invalidation on context inject
refactor(app): migrate FastAPI server structure
chore(release): v1.1.1
chore(docs): update project documentation
```

## Releases

> **Releases are performed by the maintainer, manually. Never cut a release automatically —
> no version bump+tag, no `chore(release)` commit, no `git tag` — except on an explicit request.**

Current version: **0.1.1**.

Release history (one line each; full detail in `CHANGELOG.md`):

- **0.1.1** — attachments (HTTP/CLI + web tab), `fs/download`, drop `pointer` / techprocess remnants
- **0.1.0** — first public release

Release procedure (maintainer runs this):

1. Pre-flight (all green): `pytest`, `ruff check .`, `black --check .`, `mypy core`.
2. Bump `version` in `pyproject.toml` per SemVer (pre-1.0: breaking → minor, else → patch).
3. Move `CHANGELOG.md` `[Unreleased]` → `## [X.Y.Z] — YYYY-MM-DD`; open a fresh `[Unreleased]`.
4. Update this section (current version + a one-line history entry) and `README.md` if needed.
5. Commit `chore(release): vX.Y.Z`, then annotated tag `git tag -a vX.Y.Z -m "vX.Y.Z"`.

The runtime version is read from installed package metadata (`cli/banner.py` →
`importlib.metadata`), so `pyproject.toml` is the single source of truth.
